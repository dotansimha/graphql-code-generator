# Config option examples

Every documented config option of a plugin has a generated example: a minimal schema, a minimal
operation, and the TypeScript each setting produces. Examples are generated by running the plugin.
Never write example output by hand.

## When to use this

- You add a config option to a plugin.
- You change what an existing option generates.
- You need to show an option's output (in docs, an issue or a PR description).

## Where examples live

| Plugin                  | Examples spec                                                          | Generated file                                                                 |
| ----------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `typescript-operations` | `packages/plugins/typescript/operations/tests/config-examples.spec.ts` | `packages/plugins/typescript/operations/tests/__examples__/config-examples.md` |

The spec renders the examples with `renderConfigExamples` from `@graphql-codegen/testing` and
compares them to the generated file with `toMatchFileSnapshot`. The test fails when plugin output no
longer matches the examples.

For a plugin without an examples spec, create one following the `typescript-operations` spec: a list
of `ConfigExample`s, and a `generate` function that calls the plugin.

## Adding or updating an example

1. Add a `ConfigExample` entry to the spec, in the order the options appear in the plugin's
   `config.ts`:
   - `schema` and `operation`: the smallest schema and operation that show the option's effect. Use
     one field per line. Don't share a schema with unrelated options just to save lines.
   - `variants`: the first variant is the default, with an explicit label such as
     `'myOption=false (default)'`. Add one variant per value or form the option accepts (e.g. `true`
     and the object form).
   - `sharedConfig`: options every variant needs for this option to have an effect (e.g.
     `enumType: 'native'` for enum value options).
   - `note`: only when the output alone would mislead, e.g. the option only works together with
     another option, or has no effect.
2. Regenerate the examples:

   ```bash
   pnpm vitest run --project typescript-operations config-examples -u
   ```

3. Read the generated section and check that:
   - it shows what the option changes. If the output is identical for every setting, the example
     doesn't exercise the option. Fix the schema, operation or `sharedConfig`, or add a `note`
     explaining why there's no effect;
   - each `// option=value` label matches the line it marks.
4. Commit the spec and the generated file together.

## Output format

The generated file has one section per option, with **Schema**, **Operation** and **Generated
TypeScript** blocks. The TypeScript block contains only the declarations the option changes:

<!-- prettier-ignore -->
```ts
export type UsersQueryVariables = Exact<{
  ids?: Array<string | number> | string | number | null | undefined; // arrayInputCoercion=true (default)
  ids?: Array<string | number> | null | undefined; // arrayInputCoercion=false
}>;
```

- A line that differs between settings appears once per setting, followed by `// <option>=<value>`.
  Settings that produce the same line share one comment.
- A declaration whose shape changes is shown whole for each setting, under a `// <option>=<value>`
  line.
- `(not generated)` marks a declaration a setting doesn't produce. `(added)` marks one only that
  setting produces.
- A setting that throws shows `// <option>=<value> → throws: <message>`.

Use `showWholeOutput: true` only when an option restructures the whole file (e.g.
`globalNamespace`).
